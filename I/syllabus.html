1 Course Overview

This two-semester graduate sequence covers the finite element method (FEM) from its mathematical foundations, through implementation, to applications in solid mechanics, fluid mechanics, and coupled transport problems relevant to materials and process engineering. All computational work is done in Google Colab with FEniCSx (DOLFINx 0.11). No local installation is required.

AI-based refers to how simulation code is written in this course: students are actively encouraged to use large language model (LLM) coding assistants (e.g., Gemini in Colab, ChatGPT, Claude) to write, debug, and extend FEniCSx code. The emphasis therefore shifts from typing code to formulating the problem precisely, directing the assistant, and rigorously verifying what it produces. The mathematical theory taught in the course is what makes that verification possible: a student who knows the expected convergence rate, the inf-sup requirement, or the analytical benchmark can tell when generated code is wrong.

Course Focus
AI-based Materials and Process Simulation I Mathematical foundations (Lax–Milgram, Céa, inf-sup), the internal structure of FEniCSx, nonlinear and time-dependent problems, and incompressible flow (Stokes → Navier–Stokes)
AI-based Materials and Process Simulation II Computational solid and structural mechanics (20 chapters), coupled heat and mass transfer in flows (natural convection, reactive flow, porous media), and parallel solvers

1.1 Course Format

  • Each week covers about two chapters: 3 hours of lecture (1.5 h theory and 1.5 h implementation) plus independent work in Colab.
  • Slides and notebooks are released before each lecture. Students are expected to run the notebook once before class.
  • A weekly assignment is due before the next lecture. Each lecture opens with a 10-minute quiz on the previous week’s material.
  • The term project starts in Week 8 with a proposal and runs through the second half of the semester.
  • LLM assistants may be used for all coding work. Exams and quizzes are taken without AI tools, so that each student’s own understanding of the theory and the code is assessed.

1.2 Working with LLM Coding Assistants

LLMs are fast at producing FEniCSx code, but they are frequently wrong in ways that run without error. Common failure modes include:

  • Outdated API: code written for legacy FEniCS (from fenics import *) or older DOLFINx releases (0.5–0.10) instead of DOLFINx 0.11.
  • Silent mathematical errors: wrong sign in the weak form, missing boundary terms, unstable element pairs (e.g., P1–P1 for Stokes), incorrect Jacobians, missing stabilization.
  • Plausible but unverified results: smooth-looking plots that do not satisfy the PDE, the boundary conditions, or conservation laws.

Every LLM-assisted notebook in this course therefore follows the same workflow:

  1. Formulate — derive the strong and weak forms, function spaces, and boundary conditions by hand before prompting.
  2. Prompt with context — give the assistant the weak form, the target version (DOLFINx 0.11), and the course’s API reference sheet.
  3. Read and annotate — understand every line; mark which parts were generated and which you changed.
  4. Verify — MMS convergence rates, analytical or benchmark comparison, conservation checks. Unverified code is not a result.
  5. Log — keep a short AI-usage log (key prompts, what failed, how you fixed it) in the notebook.

1.3 Learning Objectives

By the end of Course I, students will be able to:

  1. Explain the Ciarlet definition of a finite element, unisolvence, and local-to-global DOF construction, and verify them with Basix.
  2. Prove well-posedness and convergence rates using Lax–Milgram, Céa’s lemma, and the Aubin–Nitsche argument, and confirm the rates numerically with the method of manufactured solutions (MMS).
  3. Solve nonlinear problems with Newton/SNES and time-dependent problems with the θ-method.
  4. Explain the inf-sup condition. Solve the Stokes equations with Taylor–Hood elements and the Navier–Stokes equations with a splitting scheme (IPCS) and with Newton’s method, and validate against the DFG benchmark.
  5. Apply SUPG stabilization to advection-dominated problems and build block (fieldsplit) preconditioners.
  6. Use LLM coding assistants effectively to produce FEniCSx code from a mathematical formulation, and detect and correct errors in generated code through theory-based verification.

By the end of Course II, students will be able to:

  1. Solve plane-stress, axisymmetric, generalized plane-strain, and thermoelastic problems and verify them against analytical solutions.
  2. Implement plasticity, viscoelasticity, and phase-field fracture using quadrature-space internal variables and return mapping.
  3. Implement beams, plates, and shells; diagnose and cure shear locking; solve dynamics, buckling, homogenization, and cohesive-zone problems.
  4. Implement and validate multiphysics flow problems relevant to chemical engineering: Boussinesq natural convection, reactive species transport, and Brinkman flow in porous media.
  5. Run problems in parallel with MPI and analyze solver performance with AMG and block preconditioners.
  6. Lead an LLM-assisted workflow for a research-scale multiphysics simulation: decompose the problem, direct code generation module by module, and document the verification of each component.

1.4 Prerequisites

  • Course I: Undergraduate partial differential equations and linear algebra; basic Python.
  • Course II: Course I (or equivalent FEM experience); a first course in solid mechanics or elasticity; introductory transport phenomena.

2 Computing Environment — Google Colab + fenicsx-colab

from mpi4py import MPI
import dolfinx
print(MPI.COMM_WORLD.rank, dolfinx.__version__)

Complex PETSc Used only for electromagnetic and frequency-domain examples; switch with USE_CLEAN=True
Visualization matplotlib / off-screen PyVista inside notebooks; ParaView locally for result files

Participation 5% Code reviews, discussion
  • Late policy: Assignments are due before the next lecture; late submissions are not accepted.
  • Verification: Every reported number must come from a Colab notebook the student actually ran, and must be verified against an analytical solution, a benchmark, or a mesh-convergence study.
  • Reproducibility: Submitted notebooks must run end to end after “Restart runtime → Run all”. Notebooks that do not run receive zero credit.

6 Academic Integrity

  • LLM assistants are encouraged for all coding work in assignments and projects. Their use must be recorded in the AI-usage log, but it is never penalized.
  • The student is the author of record. You are responsible for every line you submit and every number you report, whoever or whatever generated it. Being unable to explain your own submitted code during a quiz, code review, or presentation is treated the same as not having done the work.
  • Exams and quizzes are closed-AI.
  • Discussing theory, mechanics, prompting strategies, and debugging with classmates is encouraged; submitting another student’s code or results as your own is not.
  • Fabricated or unverified results (e.g., numbers copied from an LLM response without running the code) are treated as academic misconduct.
